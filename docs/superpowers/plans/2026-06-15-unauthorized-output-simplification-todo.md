# 未授权检测输出收敛待办

日期: 2026-06-15

## 已确认结论

- 当前未授权降噪里的 `denyTemplateId`、`denyTemplateKind`、`denyTemplateLabel`、`denyTemplateCount` 更像内部分析过程字段，不适合作为最终漏洞结果的长期主字段。
- 这类字段对 SDK 最终输出、结果持久化模型和后续消费语义存在较强干扰，应该收敛。
- 目标应从“细分模板类型”转向“过滤相似的非未授权模板响应”，避免其污染最终未授权结果。
- 聚类能力可以保留在内部分析链路中，但不应默认泄漏到主结果模型。
- `disposition` 不应承载额外过程信息，只保留“置信度声明”这一种最终输出语义。
- `confidenceReason` 也应同步收敛为单一语义，不再保存规则拼接串，不再追加聚类模板说明，只保留一条最终声明。

## 当前倾向方向

- 主结果只保留面向用户的稳定漏洞字段，例如 `id`、`title`、`level`、`type`、`url`、`method`、`confidence`、`reason`、`dataExposure`。
- 模板聚类仅作为内部过滤或调试能力存在，不默认进入 SDK 标准输出。
- 最终结果至少应区分：
  - `confirmed`：确认保留的未授权结果
  - `suppressed`：被识别为相似非漏洞模板、默认不进入主结果的项
- `disposition` 只保留最终“置信度声明”，例如：
  - `高置信：响应包含明确业务数据返回`
  - `中置信：存在数据返回，但与公开接口仍需区分`
  - `低置信：结果更像相似拒绝模板或通用错误响应`
- `confidenceReason` 与 `disposition` 对齐，只输出单条最终声明，不再承载内部规则命中明细或聚类追加文案。

## 后续待讨论

- `suppressed` 结果是否完全不落库，还是只进入调试/审计通道。
- SDK 是否需要提供可选的 debug 输出，用于查看被过滤项。
- 最终是保留极简的 `disposition/reason` 抽象字段，还是完全不对外暴露模板过滤痕迹。
- Web 端是否保留“查看已过滤结果”入口，还是仅在内部诊断场景开放。
- 内部规则命中明细、聚类命中原因是否完全不出现在最终结果中，还是仅保留在内部诊断日志中。
